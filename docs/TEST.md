# How to test each milestone (lanes append here)

## M1 river (forge, 4612)
`cd services/forge && bun run dev`, then `bun run smoke` (PASS). Manual: `curl -s -XPOST 127.0.0.1:4612/types -H 'content-type: application/json' -d '{"name":"Refund Ranger","description":"triages billing refund bugs and replies in the house tone"}'` then `curl -s 127.0.0.1:4612/types` a few times: status goes generating, training, evaluating, ready over about 60 s (dry run: model dry-run:<id>, evalScore null). Synthetic data lands in river/runs/<id>/train.jsonl.

## M1 qm (raid-qm-plan)
QM runs as shipped from `qm/` (gitignored clone): `cd qm && HARNESS=codex bash scripts/dev-instance.sh up --surface web` (status: `bash scripts/dev-instance.sh status`). Dev slot pool1: portal http://localhost:8129 (admin /admin/), core http://localhost:8081. Model: Codex harness on Emre's ChatGPT OAuth; no keys in the repo, no secrets needed by our code (portal loopback auth bypass, principal emre).
Test: `QM_PORTAL_URL=http://localhost:8129 bun services/qm-bridge/test/smoke.ts` prints `status: ok`, a sessionId and a five-word hello from a real Codex model (about 5 s). Calls: POST /api/turn {text, threadRef} (origin header) -> runId; GET /api/runs/:id -> {status, result:{sessionId, reply}}. Codex models QM allows: gpt-5.6-sol, gpt-5.6-terra, gpt-5.6-luna, gpt-6-astra, gpt-6-sol, gpt-6-luna; effort auto/low/medium/high/xhigh.

## M1 eng (engine 4610, mock-bridge 4615, autopilot 4613)
Start, three shells from the repo root: `cd services/mock-bridge && bun run dev`, `cd services/autopilot && bun run dev`, `cd services/engine && bun run dev` (brain on 4616 seeds the Lumen world t101..t109; without it the engine uses its fixture).
- `curl -s 127.0.0.1:4610/api/state | jq '{c: (.components|length), u: (.units|length), t: (.targets|length), backend}'` -> 4 components, 6 units, 9 targets, backend mock.
- Shell A: `curl -N 127.0.0.1:4610/api/events` (first line is `state.snapshot`). Shell B: `curl -s -XPOST 127.0.0.1:4610/api/orders -H 'content-type: application/json' -d '{"unitIds":["u1"],"targetId":"t101"}'`. Shell A shows `unit.moved` steps, `unit.activity` (thinking, `gbrain.recall`, work, `gbrain.remember`) and `order.updated` with status done and a reply within about 25 s.
- Autopilot: `curl -s -XPOST 127.0.0.1:4613/propose -H 'content-type: application/json' -d '{"units":[{"id":"u1","class":"knight","team":1,"status":"idle","pos":{"x":12,"y":14},"history":[]}],"targets":[{"id":"t101","component":"billing","severity":3,"kind":"bug","status":"open","pos":{"x":3,"y":3},"customers":[]}],"memory":""}'` -> one proposal with a reason.
- Smoke tests: `bun services/mock-bridge/test/smoke.ts`, `bun services/autopilot/test/smoke.ts`, `bun services/engine/test/smoke.ts`.
Independent acceptance (raid-qm-rev, b697d86): pending-run polling fix, 2 fixture tests pass, real smoke rerun exits 0 in 3.1 s with done/ok, a sessionId and a five-word reply. Portal advertises all three class models (gpt-6-astra, gpt-6-sol, gpt-6-luna).
GBrain MCP in QM (raid-qm-plan, 9b6be9b, early M2 item): `cd services/qm-bridge && bun scripts/register-gbrain-mcp.ts` registers raid-gbrain's facade (http://127.0.0.1:4617/mcp, auth none) as QM MCP server `gbrain` by asking a QM agent (admin emre) to PUT /v1/admin/mcp-servers/gbrain with its own capability token; prints HTTP 200 and tools [recall, remember, search, get_page, add_link]. Then a QM turn "Use your gbrain recall tool with componentId billing" shows tool_call `gbrain_recall` in the run activity and the reply quotes the billing idempotency-key rule (6 s).

## M1 ui (board, 4611)
Start the engine stack first (M1 eng above), then `cd apps/board && bun install && bun run dev` and open http://127.0.0.1:4611 (`curl -s 127.0.0.1:4611/health` -> `{"ok":true,"service":"board"}`). You see the isometric map from the engine's /api/state: walled zones with banners (Billing, Onboarding, Auth, Search), the Library (GBrain) in the centre, the Forge (smithy, glowing furnace) and the Barracks, units coloured by team, bugs as monsters and features as crystals sized by severity. The top bar shows tokens, spend, Library pages, idle agents, open issues and the backend (mock).
- Left-click a monster: selection ring plus a parchment panel on the right (issue id, severity, customers, engaged units). Left-click a unit (or `raid.bus.select(["u1"])` in the console): panel with name, class, model (gpt-6-astra), status, current order, live activity feed, message box (Enter posts to /api/units/:id/message).
- Order: select a unit, right-click a target. The unit walks there and its feed fills with recall, work, remember and the reply (engine plus mock-bridge, about 25 s).
- Camera: drag to pan, wheel to zoom, WASD, H centres the Library. Esc clears the selection.
- Engine down: the board keeps a synthetic fixture on screen (backend "fixture"). Tests: `cd apps/board && bun test test/` (6 pass), `bun run typecheck`.
