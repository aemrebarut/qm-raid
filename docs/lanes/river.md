# Lane River: the Forge (the River building that trains new unit types)
Agent: raid-river (lead and implementer), reviewed by raid-rev (tell it after commits). Owns `river/` and `services/forge/`. Read the Forge API in docs/CONTRACT.md.
River docs: https://docs.river.ai/ (Python `river-client`; SFT, RL, distillation, save and serve; models such as Qwen/Qwen3.5-9B; access depends on the key; `client.get_capabilities()`). The key is `RIVER_API_KEY`; Emre sets it himself; never print it.

The feature: on the map, the Forge is a building. The user types a new agent type ("Refund Ranger: triages billing refund bugs and replies in the house tone"), the Forge generates synthetic training data for that job, fine-tunes a small model on River, evaluates it, and the user can then train units of that type from the Forge. Those units work orders like any other unit (via the Bridge API on the Forge's port), using the brain service for recall and remember.
- First step (now): `river/` Python project (venv), install `river-client`, list capabilities once the key is set (ask the Analyst for it when ready; until then build everything against a dry-run mode). Design the pipeline: (1) synthetic data from the type description plus world context from the brain service (GET http://127.0.0.1:4616/world, /search): about 100 to 300 instruction and response pairs of orders on Lumen issues answered in that type's style and rules, generated by a teacher model through River if possible (else a local template generator), (2) SFT on a small base model, (3) eval on held-out prompts vs the base model, (4) save and serve.
- M1: `services/forge` on 127.0.0.1:4612: POST /types and GET /types with the stage machine (dry run: fake progress over about 60 s so the UI can be built), GET /health.
- M2: the real pipeline end to end once for one type (data, SFT, eval, served model id). Report timings; if training takes longer than a few minutes, keep a pretrained type ready for the demo and show live progress for a new one.
- M3: Forge units via the Bridge API on 4612: an agent loop on the served model that recalls from the brain before and remembers after each order, streaming activity and a reply.
- M4: honest eval numbers (trained vs base on the held-out set) visible in GET /types (`evalScore`); optional: a commander type trained on data/vetoes.jsonl answering POST /propose.
