## What QM gives us (read from the QM source, main @ clone time)
- Core API is "source-authenticated": every request carries HMAC headers from `CORE_SIGNING_SECRET` plus a portal identity header minted with `PORTAL_IDENTITY_SECRET` (`{p: principalId, exp}`). Reference: `qm/src/auth/source-auth-sign.ts` (`signedRequestHeaders`), `qm/src/auth/signed-token.ts` (`mintSignedPayload`), usage in `qm/src/deployment/postdeploy-smoke.ts` (`stagingApiHeaders`, `checkLiveSession`). We re-implement the signing in our own file (no imports from qm/). Admin routes also need `x-admin-actor: <principal>@<orgId>`.
- Start a turn: `POST /v1/turns` (add `?async=1` to get `202 {runId, sessionId, status:"queued"}` instead of waiting). Body:
  `{"surface":"web","actor":{"externalId":P},"conversation":{"kind":"dm","threadRef":"web:P:raid-<unitId>"},"text":"...","origin":{"kind":"human"},"addressed":true,"idempotencyKey":"<uuid>","model"?,"harness"?,"thinkingLevel"?}`. Same threadRef = same session, so one unit = one threadRef.
  Sync reply shape: `{status:"ok", sessionId, reply, runId?}`.
- Stream a run: `GET /v1/runs/:runId/events` is SSE in AG-UI style: `RUN_STARTED`, `TOOL_CALL_START {toolCallId, toolCallName, args}`, `TOOL_CALL_RESULT {toolCallId, content, isError}`, `CUSTOM name=delta {offset, delta}` (reply text), `CUSTOM name=run {run}`, `RUN_FINISHED`. Heartbeat every 15 s. `GET /v1/runs/:id` for final state.
- Read a session: `GET /v1/sessions/:id?viewer=P&tailTurns=1` (paging is `sinceSeq`/`tailTurns`/`beforeSeq`; `after`/`waitMs` exist only on the swarm read) gives `{session:{title}, entries:[{type:"user"|"assistant"|"tool_call"|...}]}`. Archive: `POST /v1/sessions/:id {principalId, archived:true}`.
- Swarms (docs/swarms.md): agent API `POST/GET /v1/swarm` needs an agent capability token bound to a live run; human API `POST/GET /v1/sessions/:id/swarm` needs a signed portal identity and, to initialize a root, a `runId` of that session by the same actor. Spawn `{action:"spawn", requestId, contexts:[{group, role, unitId}], text}`; read `?read=1&after=<seq>&waitMs=10000`; context only replaces the caller's own context. Needs Postgres stores (dev instance has them) and `SANDBOX_RESOURCES_ENABLED=true`; each worker gets its own blank Docker computer.
- QM's MCP client (qm/src/mcp/mcp-client.ts) is stateless: POST JSON-RPC to `<url without /mcp>/mcp`, only `tools/list` and `tools/call {name, arguments}`, no `initialize`, no session id; auth `none`, `bearer` or `client_credentials` (POST `<base>/token`). Accepts JSON or SSE replies. `gbrain serve --http` needs OAuth 2.1, so raid-gbrain serves a small auth-none facade on 127.0.0.1:4617/mcp instead (proposed tools: search, get_page, recall, remember, add_link).
- MCP tools for agents: `PUT /v1/admin/mcp-servers/:id` `{name, url, auth:"none", credentialScope:"shared", readOnly:false, enabled:true}` registers an HTTP MCP server org-wide (loopback http is allowed for local dev). Memory-provider route needs OAuth, so we use the MCP registry.
- Dev instance: `bash scripts/dev-instance.sh up --surface web` (core + workers + web + portal on a port block from 8080; local Docker sandbox; local Docker Postgres). `status`, `logs [child] -f`, `doctor`, `down`. Env from shell, `~/.config/qm/dev.env`, `qm/.env`. `DEV_INSTANCE_ALLOW_MOCK=1` = no model (wiring only). Local portal auth bypass signs in as the admin principal.

## Decisions
- Transport: M2 ships **one QM session per unit** (threadRef `web:<P>:raid-<unitId>`). Swarm is an M3 experiment for teams, timeboxed 20 minutes, only kept if it works end to end.
- Auth (14:58, from raid-qm-impl, approved): secret-free. The bridge talks to the **portal** (`QM_PORTAL_URL`, dev slot pool1: http://localhost:8129), whose `PORTAL_LOCAL_AUTH_BYPASS` signs loopback clients in as principal `emre`. Relay routes: `POST /api/turn {text, threadRef:'web:emre:raid-<unitId>', model?, harness?, thinkingLevel?}` -> core `/v1/turns?async=1` -> `{status:'queued', runId}`; `GET /api/runs/:id/events` (core run SSE); `GET /api/runs/:id` -> `{status, result:{sessionId, reply, adminUrl}}`; `GET /api/sessions/:id?sinceSeq=`. Non-GET requests need header `origin: <portal url>`. Signed core headers (`src/qm-auth.ts`) only as a fallback for routes the portal does not relay.
- Terminal mapping (from raid-qm-rev): `RUN_FINISHED` is also sent for failed runs (qm/src/api/routes/run-events.ts:97), so reply vs error comes from the `CUSTOM name=run` value (status, result) or `GET /api/runs/:id`. The replay snapshot on reconnect carries `run.partial`, not delta replays. Exactly one terminal event per orderId.
- Tool names: QM names MCP tools `<serverId>_<toolName>` (qm/src/mcp/mcp-tool-service.ts:113), so with server id `gbrain` we get `gbrain_get_page`. Normalize any tool whose name starts with `gbrain` to `gbrain.<op>` (strip `gbrain_`, `gbrain-`, `gbrain.`, `mcp__gbrain__`), so the engine sees `gbrain.search`, `gbrain.get_page`, `gbrain.put_page`, `gbrain.add_link`, `gbrain.recall`, `gbrain.remember`.
- GBrain MCP (contract v3): services/brain owns the game brain and exposes an MCP facade at `http://127.0.0.1:4617/mcp` (raid-gbrain). We register it in QM with the admin MCP route. QM core runs on the host, so 127.0.0.1 works; sandboxes would need host.docker.internal but MCP calls are made by core.
- Model: Emre approved `HARNESS=codex` (his ChatGPT OAuth via `~/.codex/auth.json`; no Anthropic key). Workers are Codex-harness QM agents. The engine's class models (claude-*) are not available, so the bridge maps every unit's `model` to a Codex model QM accepts (default: whatever the dev instance picks; per-class variety only if QM exposes several Codex models) and reports the real model in activity text. From source: core refreshes the OAuth token centrally and writes a derived auth.json (access token only, no refresh token, mode 600) into a temp host jail CODEX_HOME for the codex app-server child (qm/src/harness/codex-harness.ts:255-285, 904-910); the Docker sandboxes do not get it.
